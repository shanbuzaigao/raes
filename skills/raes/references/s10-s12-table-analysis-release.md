# S10 Master table and effect sizes, S11 Analysis, S12 Release and reproduction

These stages differ from project to project. The skill helps with the structure and the records; the statistics belong to the researcher's analysis plan.

## S10 Master table and effect sizes

- Code builds the master table from the per-paper outputs. Each row receives a stable identifier from a registry: normal builds are read-only and fail on an unregistered row; allocating new identifiers needs an explicit flag; retired identifiers are never reused.
- Effect sizes are computed by code from the coded inputs, by the paths the analysis plan declares. The synthetic example in the RAES repository (`examples/synthetic/effect_sizes.py`) shows two paths (means and standard deviations; events and totals) with their formulas documented; a project uses the paths its plan specifies.
- Ask: the identity fields; the computation paths and formulas the plan specifies; which second package will recompute the pooled results.
- Check: every effect is recomputed by a separately written script from the stored inputs. That is the independence meant here; a second statistical package comes in S11, for the pooled results.
- Three rules the plan should give before the table is built: how a dispersion with an unclear label is read (SD and SE labels in conflict, no label, or a label that the report's own numbers contradict), and that every effect read this way is flagged; which measure represents a study when its main measure cannot be computed, which needs the rank of every measure in the table; and what happens when a planned imputation finds nothing to impute from. Check a special-case rule against the coded values before writing it down.
- Analysis scripts read the master table and nothing else, so everything they need has to be in it, including readable study labels for tables and figures.

## S11 Analysis and statistical validation

- Analysis scripts read the frozen master table and nothing else.
- The skill does not choose models or tests. Ask what the analysis plan specifies, including which construction choices will be checked (dependence among effects from the same paper, alternative constructions, sensitivity to comparison-data sources, publication-bias diagnostics, power), and help record it in `analysis/PLAN.md`.
- Check: each block ends with an independent numerical check of the reported values. The check is independent of the selection code only if the second package rebuilds every block's dataset from the master table itself, instead of reading the datasets the first script wrote.

## S12 Release and reproduction

- Each completed stage is saved as a dated release that is never edited. A release can be a copy of the files, or an inventory of their hashes in place; the inventory avoids duplicating a large project inside a synchronized folder. `python scripts/release.py --project <project> create <name>` writes the inventory (`releases/<name>/MANIFEST.json`, every project file with its size and SHA-256), `activate <name>` writes `releases/CURRENT` (the name and the manifest's hash, so the pointer cannot silently point at a changed manifest), and `verify` compares the working copy with the release. `activate` also writes `releases/<name>/ACTIVATION.md` with the time, the manifest's hash and the release it supersedes; add there what the release makes current.
- What a release covers: every file of the project except the release folders, `releases/CURRENT`, and the paths listed in `releases/LEFT_OUT.txt`, which is for reports that every run rewrites. The decision log and the status file are covered, so an entry made after a release makes `verify` fail until a new release is made; say so in `releases/README.md`. Write the log entry about a release before creating it ("released from the state after this entry"); what is known only afterwards goes into the activation record, which no inventory covers. An activation record next to the manifest says what the release makes current and what it supersedes. The status file records completed work as complete and does not attach inferred next steps.
- Every new project has `run_pipeline.py` and `pipeline.json` in its root. List each coded stage in `pipeline.json` as it is finished: its command, writing into `{out}`, and its formal outputs with the rerun file each is compared with; list the frozen inputs and programs under `fixed_files` and `fixed_folders`. `python run_pipeline.py --write-manifest` records the expected state after an approved change (the previous manifest goes to `archive/`; log the new manifest's hash with the decision), and `python run_pipeline.py` reruns everything into a folder outside the project and stops at the first difference. With `--copy` it first copies every file the manifest names to that folder, checks each copy by hash, and reruns inside the copy; every program a stage runs has to be listed under `fixed_files` for this.
- One command copies the formal inputs to a fresh location outside any synchronized folder, switches off network access and rebuilds the results from the saved responses. `python scripts/run_offline.py -- <command>` runs a command with network access switched off for the Python processes it starts and tests the guard first. Write the rebuild command and what it covers into `REPRODUCE.md`. A step that cannot be rerun, such as retrieving full texts in a browser, enters the rebuild as frozen, hashed files.
- A rebuild compares its outputs with recorded hashes, so a script whose output carries a time stamp cannot be compared byte for byte: leave the stamp out, or compare the record lines.
- Software environments and disposable caches live outside synchronized folders.
